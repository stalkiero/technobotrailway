# Журнал Техно — Telegram-бот

Реалізація ТЗ на **Python 3.12+ / aiogram 3.x / SQLite (aiosqlite) / FSM**.

## Структура проєкту

```
tehno_zhurnal_bot/
├── main.py            # точка входу
├── config.py           # токен, типи виходів, налаштування
├── database.py          # окрема SQLite-база на кожного користувача (data/<user_id>.db)
├── states.py           # FSM-стани майстра Д/З
├── keyboards.py         # inline-клавіатури
├── timers.py            # реєстр активних asyncio-таймерів
├── utils.py             # форматування часу/картки виходу
├── handlers/
│   ├── start.py         # /start, головне меню
│   ├── journal.py        # журнал виходів, таймер, ліміт "1 вихід/годину", затримка
│   ├── report.py         # звіт
│   ├── clear.py           # очищення журналу
│   └── homework.py        # майстер формування Д/З (6 кроків)
├── requirements.txt
└── data/                # тут з'являються *.db файли користувачів
```

## Встановлення та запуск

```bash
python3.12 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

export BOT_TOKEN="ВАШ_ТОКЕН_ВІД_BOTFATHER"   # Windows: set BOT_TOKEN=...
python main.py
```

Токен можна також прописати напряму в `config.py` (константа `BOT_TOKEN`),
але рекомендовано використовувати змінну середовища.

## Як реалізовано ключові вимоги ТЗ

- **Головне меню та всі розділи** — на inline-кнопках, без текстових команд (окрім `/start`).
- **Журнал виходів** — вибір типу → картка з кнопкою «✅ Вийшов» → активна картка
  з живим таймером (оновлюється кожні 20 сек) і кнопками «🔙 Прийшов» / «⏳ Затримка (+5 хв)».
- **Логіка «Затримка»** — окрема позначка `delayed` у базі; у звіті додається
  суфікс "(затримка)" лише якщо кнопку справді натискали, тривалість при цьому
  просто не показується окремо — рахунок ведеться від фактичного часу початку/кінця.
- **Ліміт "1 звичайний вихід на годину"** — рахується по календарній годині
  (`YYYY-MM-DD-HH`), автоматично скидається на початку нової години. Другий вихід
  у межах тієї ж години показує попередження з кнопкою підтвердження.
- **Звіт** — формується з таблиці `exits` конкретного користувача, або
  "Журнал порожній.", якщо записів немає.
- **Очищення журналу** — з підтвердженням, видаляє записи, лічильники годин
  і активний вихід.
- **Формування Д/З** — покроковий FSM-майстер (дата → день → варіант → кількість
  завдань → сторінки Д/З → фото товарів по кожному завданню); після сторінок
  бот публікує їх одним повідомленням (медіа-групою), а для кожного завдання —
  окреме повідомлення з усіма фото цього завдання.
- **Окрема база для кожного користувача** — `data/<telegram_user_id>.db`.
- **Асинхронність** — весь бот на `asyncio`/aiogram 3, таймер виходу працює
  як фонова задача `asyncio.create_task`, що не блокує обробку інших користувачів.

## Деплой на безкоштовний хостинг (Railway) через GitHub

1. Заливаєте цю папку в новий репозиторій на GitHub (файли `Procfile`,
   `runtime.txt`, `.gitignore` вже готові — файли `data/*.db` в репозиторій
   не потраплять завдяки `.gitignore`).
2. Реєструєтесь на [railway.app](https://railway.app) через GitHub-акаунт.
3. **New Project → Deploy from GitHub repo** → обираєте цей репозиторій.
4. Railway сам розпізнає `Procfile` і запустить `worker: python main.py`
   як фоновий процес (HTTP-порт не потрібен — це не веб-сервер, а
   long-polling бот).
5. У вкладці **Variables** додаєте змінну середовища `BOT_TOKEN` зі
   значенням токена від @BotFather.
6. (Рекомендовано) У вкладці **Volumes** підключаєте постійний диск і
   монтуєте його в `/app/data` — інакше при кожному передеплої бази
   користувачів (`data/*.db`) можуть губитися, бо диск на безкоштовному
   тарифі ефемерний.
7. Deploy → у логах повинно з'явитися `Start polling` — бот живий.

Безкоштовного ліміту Railway (≈500 год/міс, 512 МБ) вистачає для одного
бота, що працює постійно. Якщо ліміт вичерпається — сервіс просто
зупиниться до початку наступного місяця (або можна прив'язати картку і
доплачувати лише за перевищення).

### Альтернатива — Render

На безкоштовному тарифі Render — це «Web Service», який засинає без
вхідних HTTP-запитів. Для long-polling бота знадобиться:
- додати мінімальний `aiohttp`/`Flask` health-check ендпоінт, який слухає
  порт з `PORT`, щоб Render вважав сервіс "живим";
- підключити зовнішній пінгер (наприклад, UptimeRobot) раз на 10 хв на
  цей ендпоінт, щоб сервіс не засинав.

Це робочий, але менш прямолінійний варіант — тому для цього проєкту
простіше почати саме з Railway.

## Що можна донастроити

- У `config.py` — тривалість перерви/обіду, крок таймера, розмір затримки.
- У `handlers/homework.py` — куди публікувати Д/З (зараз — у той самий чат,
  де відбувається діалог; за потреби легко перенаправити в інший чат/канал
  за `chat_id`).
- Для продакшн-навантаження краще перенести `active_timers` та FSM-сховище
  (`MemoryStorage`) у Redis/PostgreSQL, щоб таймери й стани переживали
  перезапуск процесу.
